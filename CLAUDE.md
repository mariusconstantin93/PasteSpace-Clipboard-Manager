# PasteSpace — Architectural & Security Guidelines

You are a senior macOS architect for **PasteSpace**, a sandboxed, privacy-first, 100% offline menu-bar clipboard manager (freemium: free tier + one lifetime non-consumable IAP). These rules describe the code AS IT EXISTS — do not propose alternatives unless asked.

## 1. Target & Language
- Deployment target **macOS 14.0**; Universal Binary. Development happens on newer macOS betas — gate any macOS 15+ API with `if #available(macOS 15.0, *)`.
- **Swift 6, `SWIFT_STRICT_CONCURRENCY = complete`** (both targets). Isolation pattern in use: `@MainActor final class` for engines/managers/view models, `struct … : Sendable` for stateless services (`OCRService`, `SensitivityDetector`, `DataMagicEngine`), `OSAllocatedUnfairLock` for the rare cross-thread cache. `DatabaseManager` is the deliberate exception: a non-isolated `final class … Sendable` whose `async throws` methods hop to GRDB's serialized queue. No `actor` types exist — do not introduce one without justification. No Combine, no `ObservableObject`; state uses `@Observable`.

## 2. App Shell & UI
- **AppKit shell + SwiftUI content.** `clipboard_managerApp` is an empty `Settings` scene whose only job is `@NSApplicationDelegateAdaptor`; everything real lives in `AppDelegate`. `AppDelegate` owns `NSStatusItem`, a `ResizablePanel: NSWindow` hosting SwiftUI via `NSHostingView` (`ZeroSafeAreaHostingView`), `LSUIElement = true`, activation policy `.accessory` (temporarily `.regular` only for StoreKit/auth sheets). Popovers are SwiftUI `.popover`. Quick Look is a custom `QuickLookManager` (`NSWindowDelegate`). Global hotkey uses Carbon `RegisterEventHotKey` (sandbox-safe; never `CGEventTap`/Accessibility).
- `AppDelegate` also owns the object graph and injects it: `DatabaseManager` → `ClipboardEngine` → `ClipboardViewModel`, plus `SettingsManager`, `ProManager`, `GlobalHotkeyManager`. Wiring is callback-based, not Combine: `ClipboardEngine.startMonitoring(handler:)`, `ClipboardViewModel.onRequestClosePopover` / `onRequestRefocus`, `ProManager.onProStatusChanged`.
- A large, load-bearing part of `AppDelegate` is menu-bar status-item resilience (recovery observers, exponential-backoff re-creation, macOS 27 status-bar thickness handling). Treat that code as intentional; do not "simplify" it away.
- Views stay thin; logic lives in `ClipboardViewModel` (the app's largest type — paste flow, vault reveal/mask, selection, search, OCR refresh, maintenance), `SettingsManager` (every preference is a `didSet`-backed `UserDefaults` mirror), `ProManager`, `StoreManager`.
- `ClipboardItem` is a value type; its `Equatable` must include every field that affects row rendering (`ocrText`, `vaultLabel`, `bookmarkData`, `richContent`, `pasteContent`).
- **Row layout.** A row is a `VStack`: content across the full width, then a 20 pt bottom bar — buttons left (aligned with the text), `source · time` right (the source name truncates first, the time never). The type icon sits in its own 30 pt leading column, centred across both and drawn behind them. Tap/drag lives in `rowInteraction(_:)`, applied to the icon column and the text but never to the bar, since the AppKit drag overlays win hit-testing over the buttons. Each overlay is mounted **once**, in front (`.overlay`) — the front copy is the one that takes the gesture, and the list is a `LazyVStack`, so a row's `NSView`s exist only while it is on screen. The row's padding sits inside its two halves, not around them, so no band of it is dead to clicks. The bar itself still selects the row: a plain `.onTapGesture` on the bar `HStack` catches its empty space and `source · time`, while the nested buttons take their clicks first. Keep that gesture on the bar and plain — never on an ancestor of the row (an ancestor also fires for clicks the AppKit overlays already handled, so one ⌘-click selected and deselected), and never `rowInteraction` (its overlays would swallow the buttons). Buttons are faint until hover/keyboard focus/open popover; from two selected rows up (`hasMultiSelection`) every row hides its buttons and selected rows show only their ordinal badge — batch actions belong to the selection bar.
- **Rows redraw only when what they draw changes.** `ClipboardRowView` is `@MainActor Equatable` on its 22 value inputs and the list applies `.equatable()`. The ~40 action closures are excluded on purpose: the list recreates them on every render and SwiftUI cannot compare closures, so every visible row's body re-ran on every change the list saw — each step of the keyboard highlight, thirty a second while an arrow key was held, which starved the screen until the key came up. The closures capture only the item (compared) and long-lived objects and read everything else when they run, so equal inputs mean identical behaviour. **A new stored property a row draws from must be added to `==`**, or the row won't redraw when it changes. Keyboard focus follows with `scrollTo(id, anchor: nil)` — the minimal scroll that keeps the row visible — and without animation when steps arrive within 0.2 s of each other (a held key): a fresh animation every 33 ms never finished.
- **A row never waits on the disk or on whole documents while drawing.** Rows are built as they scroll into the `LazyVStack`, on the main thread, so anything slow in `body` is a stutter — scrolling past two copies of a web page from Safari (171,548 characters in 487 KB of RTF each) froze the list for about a second. Three rules came out of it: **(1) rich-text previews are the first `textPreviewMaxLength` characters** — `previewHead(of:)` parses the RTF off the main thread and cuts it, `buildRichPreview()` adapts and converts the 200 characters on the main thread (the adaptation resolves against the appearance) and caches them; `cachedPreview(for:)` only looks up, and the row shows the plain preview until the rich one is ready. Before, each such row cost 105 ms to build and 180 ms of SwiftUI text layout every time it came into view, even under `lineLimit(2)`; now 0.1 ms and ~5 ms. **(2) File status comes from `FileStatusStore`**: existence, Trash, kind and a group's missing count, checked once per appearance on a background queue and remembered — `fileExists` goes through the security-scoped bookmark, an IPC round trip, and the row used to call it three or four times per draw (once per member for a group), on every hover too. Until the first answer the row assumes the file is there. **(3) `ClipboardItem.textPreview` decodes only the first `textPreviewMaxLength × 4` bytes, and `isWebURL` answers no without decoding for content over 64 KB** — both run on every draw.
- **Reordering auto-scrolls.** SwiftUI's `ScrollView` does not auto-scroll during a drag on macOS, so a row could only be moved among those on screen. `ReorderAutoScroller` (in `ClipboardListView.swift`) starts with each drag (`ReorderDragSource.begin`), runs at 60 Hz in common run-loop modes (a drag tracks the main run loop in event-tracking mode), finds the history's `NSScrollView` — SwiftUI's `HostingScrollView`, the tallest scroll view in the panel — and moves its clip view when the pointer is within 52 pt of the top or bottom edge or up to 40 pt past it, eased from a crawl to ~1,000 pt/s. It stops by itself once the mouse button is up, not on the sessions' end callbacks (their order against the drop isn't guaranteed), and scrolls only while `canReorder` holds, so a drag on its way out to another app never moves the list.
- **Row details.** The copy time is an absolute date and time (`copiedAtText`, locale-aware, year only for other years) — nothing refreshes rows on a timer, so relative times went stale. An ⓘ left of the source opens `RowDetailTooltip` (a custom non-activating panel: 0.35 s on hover or at once on click) with only what the row does not show: kind and counts, `CodeLanguageDetector` language for code, full link, file path/kind/size, folder size (summed off-main through the bookmark, capped at 100k items / 3 s), image dimensions, edit status and auto-removal date. Locked Vault items show nothing but "Protected". A document whose text was read reports `Extracted text: N characters · formatted` there, and any row whose text has been read out of it — an extracted document, a recognised image or scan — carries a small `text.viewfinder` badge on its type icon — a mark, not a control, because the text is read in Quick Look rather than copied wholesale, and a decorative glyph among the row's buttons would invite clicks that do nothing. Never badged while locked. `CodeLanguageDetector` runs on the main thread: keep its regexes free of nested repetition (catastrophic backtracking) and its sample bounded.
- **Search carries filters and a sort.** The field (`SearchBar`, which now takes a `trailing` slot) holds a filter button and a sort menu; `SearchFilterBar.swift` has both plus the popover and `FilterChipsRow`. **The chips matter more than the popover**: a filter silently left on looks exactly like lost history, so every criterion in force is drawn under the field and one click removes it. The sort is persisted (`SettingsManager.listSort`) because it is a preference; the filter is **not** — it starts empty on every launch, being a question the user is asking now. Filtering by kind and every sort order are free; combining criteria is `Feature.advancedSearch`, and `ClipboardViewModel.effectiveFilter` collapses a free user's filter to `kindsOnly` so the list can never disagree with the popover, whose advanced half is dimmed and inert rather than hidden. `isListNarrowed` (text **or** criteria) is what stops the multi-selection being pruned — absence proves deletion only when everything is visible — and `canReorder` (custom sort **and** not narrowed) gates both `moveItem` and the drop target's `validateDrop`, so no insertion line ever promises a drop that will be refused.
- **The Pinned section folds.** Pinned rows sit above the history, so a long pin list fills the panel's default height and pushes every recent copy below the fold. Its header (`ClipboardListView.pinnedSectionHeader`) is a button reading `PINNED (4) ▸` — title, count, then an `arrowtriangle.right.fill` at `.caption` so the glyph matches the title's size, rotated 90° when open. Both section headers carry their own count (`RECENT (103)` too): the footer's total covers the whole history and says nothing about the split, and a pinned row is not counted among the recent ones. The state lives in `SettingsManager.pinnedSectionCollapsed` (remembered across launches, deliberately absent from the Settings UI — the header is its only control). **`selectedIndex` walks `ClipboardViewModel.visibleItems`, not `pinnedItems + unpinnedItems`** — that is what keeps keyboard focus off a folded row, and any new navigation or focus code must use it too; only the reorder path still reads the full list, because it is about stored order rather than what is on screen. It is a position, so `reloadItems` puts it back on the same item by id (`restoreKeyboardFocus`), or clears it when that item is gone — a copy landing on top used to slide the highlight onto another row — and `clearKeyboardFocus()` ends it when the panel hides (`hideAllPanels`), after a paste with Always on top, on a mouse ⌘/⇧-click, on a new search or filter, and on Esc (after the multi-selection, before closing). It used to outlive all of those. A search always shows everything (`isPinnedCollapsed` is false while `searchText` is non-empty): hiding a row the query matched would make the result lie. Folding drops keyboard focus and removes pinned rows from a ⌘-click selection, so a batch action can never reach a row nobody can see; "Show in History" unfolds the section when the item it wants is pinned.
- **"Open at mouse cursor" puts the pointer on the newest Recent row**, not on the middle of the panel — opening under the cursor is for grabbing the thing just copied, and the panel's centre is wherever the history happens to reach. Rows are variable height, so the offset is measured rather than computed: `ClipboardListView` measures the row at `visiblePinnedCount` with `onGeometryChange` (back-deployed to macOS 13) in the panel's named coordinate space and writes it straight into `RecentRowAnchor.shared`, a lock-protected box that also records which row wrote it; the row's `onDisappear` clears it only if that row still owns it, so a row that has just become the newest is not erased by the old one leaving. It is deliberately **not** view-model state — a measurement that invalidated the view that produced it is the shape of the layout recursion this tree has had before — and deliberately **not** a preference: that was the first version, and SwiftUI reported "Bound preference … tried to update multiple times per frame" whenever the list reloaded under it. `panelSpace` is `nonisolated` because the geometry transform is a `@Sendable` closure. `positionPanelAtMouseCursor` falls back to centring whenever there is no measurement (first launch, or the row scrolled out of the `LazyVStack`, which clears it), and the existing screen-edge clamping still wins, so near an edge the pointer lands wherever the panel could actually fit. The value can be one copy stale if the list never laid out while hidden; the row is still within a row's height of the pointer.
- **The global shortcut respects "Always on top".** `togglePanel` is otherwise a plain toggle, which meant a pinned panel — always visible — could only ever be hidden by the shortcut. While `alwaysOnTop` is on *and the panel is on screen*, the shortcut moves it to the pointer when `openAtMouseCursor` is also on, and does nothing otherwise; hiding belongs to the close button and the menu-bar icon. The visibility check matters: closing the panel by its own button must leave the shortcut able to bring it back.
- **Retention.** "Keep history for" (`SettingsManager.historyRetentionDays`, 0 = Forever, default) sets `expiresAt`; the history limit still applies alongside it. `DatabaseManager.applyRetention` re-derives every unpinned, non-Vault expiry from `timestamp` at launch and on change; re-copies renew it and unpinning starts a fresh lifetime. There is no fixed TTL in `AppConstants` any more.
- **Captured rich text is display-adapted, never rewritten.** `NSAttributedString.displayAdaptedForReading()` (`Utilities/AttributedStringDisplay.swift`) is used by the row preview and Quick Look's read-only view: a run with its own background keeps the source foreground, an unreadable pair (contrast < 2:1) gets black or white, and a run without a background falls back to `labelColor` when near-black or near-white. The editor, the pasteboard, drags and Share always use the stored RTF unchanged.
- **The app icon is drawn on Apple's macOS grid, not full-bleed.** `AppIcon.appiconset` holds the shape at 824×824 inside a transparent 1024 canvas, with smooth (superellipse) corners and the template's soft shadow in the margin. macOS 14–15 draw an icon exactly as supplied, so the shape must be in the image; macOS 26 recognises an icon on this grid and draws it as-is. The previous icon was an opaque full square with its own inner tile and a white surround, and macOS 26 cut *that* whole square into its rounded shape — a white icon with a smaller dark icon inside, the artwork at about half size. Check any new icon the way the system sees it — `NSWorkspace.shared.icon(forFile:)` on a built copy at a fresh path (Icon Services caches by path) — and on a macOS 14/15 machine before release. macOS has no alternate-icon API, and rewriting the bundle's icon would break its signature, so there is one icon; a "Pro" variant can only ever appear inside the app. **The menu-bar icon is where Pro shows** (the user's choice among mock-ups, option F): while `proManager.isPro`, `AppDelegate.makeMenuBarIcon()` returns `proMarkedMenuBarImage` — the clipboard with a small solid "PRO" tag over its bottom-right corner, the letters cut out of the tag and a 1-unit gap cut around it, proportions on an 18-unit square scaled to the bar's icon size. It stays a template (single-colour, so the bar tints it; a coloured badge would not follow Liquid Glass) and is **rendered into 1× and 2× bitmaps**, never a drawing-handler image: on macOS 27 the button lives in a system XPC process and the image must reach it as pixels. **The clipboard in it is drawn at the symbol's natural size** (`makeMenuBarSymbol()`, 16 × 18 pt for `doc.on.clipboard` at 13 pt), never at the 14 pt layout square `makeMenuBarTemplateImage()` assigns: the menu bar draws a *symbol* image at its natural size whatever `size` it is given (the log showed the free button 28 × 31 around a "14 × 14" symbol), while a bitmap is drawn at exactly its own size — the first Pro version squeezed the clipboard into 14 × 14 and looked much smaller. The tag reaches past the clipboard to the right (24 × 18 pt in all), and the status item is as wide as that image, or the button's `.scaleProportionallyDown` would shrink the whole image to fit. Checked by the user on macOS 26 and 27. **The status item's length is the icon's own width** (`menuBarIconWidth`: 16 pt free, 24 pt Pro; `statusItemLengthInUse`, which the fast path compares against): macOS adds 8 pt on each side of every item's slot and sizes a standard item's slot to its image (measured on 26 — the clipboard symbol makes a 32 pt item, a 24 pt image a 40 pt one, and the built-in icons span 32–44 pt the same way). The fixed 28 pt it replaced still creates the item (`menuBarStatusItemLength`, kept fixed for the Tahoe zero-width race) and is the fallback without an icon, but left in place it put 6 pt of extra padding on each side, which the user saw as PasteSpace standing further from its neighbours than the system icons. Every icon assignment goes through `configureStatusItemButton` → `makeMenuBarIcon()`, so launch (Pro read from the cached status, so an existing Pro user never sees the plain icon first), each recovery and the nuclear re-creation draw the right one; `onProStatusChanged` calls `refreshMenuBarProMark()`, which forces a full configure (`"pro-status"` is in `statusItemReasonsRequiringFullConfigure`) only when the mark would actually change — StoreKit reports the same status at every launch. The tooltip reads "PasteSpace Pro" with it.
- **Share** (`Utilities/ShareCoordinator.swift`): `NSSharingServicePicker` for every item type, free in both tiers, toggled by `settings.shareEnabled`. Locked Vault rows authenticate first and re-mask afterwards; file shares hold their security scope until the chosen service reports back. No entitlement, no network call of our own.
- **"Paste" never synthesizes a keystroke.** `ClipboardViewModel.pasteItem(_:forcePlainText:)` writes to `NSPasteboard.general`, then `AppDelegate` hides the panel and re-activates the stored `previousApp` so the user presses ⌘V themselves. There is no `CGEvent` posting anywhere — keep it that way (it would need Accessibility permission and break the sandbox story).
- Where the bulk of the code actually is, in size order: `ClipboardRowView.swift` (~3.1k lines — row rendering, per-type previews, drag-path selection, multi-selection drag, vault drag auth), `QuickLookManager.swift` (~3.1k — the Quick Look window plus the whole rich-text editor: `RichTextEditorState`, formatting toolbar, colour/font popovers, `EditableRTFView`/`SelectableRTFView` `NSViewRepresentable`s), `ClipboardViewModel.swift` (~2.2k), `AppDelegate.swift` (~1.5k), `VaultFilePromiseDrag.swift` (~1.3k — all AppKit drag sources). Read the `// MARK:` outline of these before editing; several distinct types share one file.

## 3. Clipboard Pipeline
- `ClipboardEngine`: `DispatchSourceTimer` on the main queue (0.5 s, 100 ms leeway) polling `NSPasteboard.general.changeCount`. Never replace with `Task.sleep` loops (CPU/wake-up regression).
- Captures text/RTF, URLs, images, file URLs; records source app bundle ID + name; skips items carrying the app's own internal marker type and `AppConstants.transientPasteboardTypes`.
- Order of gates before persistence: password-manager source → ignored/system apps → user App Blocklist → size limit. The size limit (`AppConstants.maxItemSizeBytes`, 10 MB) applies to **text only**, the one kind of content the list still loads whole. Images copied as image data have none — their bytes never enter the list (see §7) — and neither do files, which are stored as a path and a bookmark.
- **A password-manager copy is either locked or not stored.** With *Capture from password managers* on (`vaultEnabled && vaultCapturePasswordManagers`, both default true), the engine lets copies from `AppConstants.passwordManagerBundleIDs` through — concealed types included — on the promise that they go straight into the Vault. The engine cannot keep that promise on its own: whether a row can be locked is decided later, in `ClipboardViewModel.handleNewItem` (a free Vault already holding `freeVaultLimit` items, or encryption failing). So `handleNewItem` drops any password-manager copy that ends up unlocked, and `handleNewItemInMemory` (the no-database fallback, which has no Vault) drops them outright. Before this, a free user with a full Vault had the password stored as readable, searchable text — worse than the option being off, which blocks the copy. Ordinary auto-detected secrets are different on purpose: once the free Vault is full they are stored like any other item, because the user copied them in an ordinary app.
- **Drag & drop.** Nothing is ever *captured* by dropping onto the app; the only drop target is in-list reordering. The drag-out code is split across paths because SwiftUI `.onDrag { NSItemProvider }` publishes promised *data* types that destinations probe mid-drag (breaking Vault auth and some Electron targets) — the rationale is in the header of `VaultFilePromiseDrag.swift`; read it before touching drags. `ClipboardRowView` picks one path per drag:
  - **vault-promise** — `NSFilePromiseProvider`; Touch ID/password and decryption happen in `writePromiseTo:`, i.e. only after the drop commits. Every promise in one drag shares a `VaultDragAuthGate`: destinations materialise promised files concurrently, and N simultaneous `evaluatePolicy` calls make macOS show one dialog and fail the rest, so only one item would arrive. One gate per drag session — never per row. A row the user has already **revealed** does not take this path at all: it drags its real text or file URL, in a multi-selection exactly as it always did on its own (`needsVaultPromise`, `revealedContentFor`). That is the same rule Copy and Share follow for an unlocked row — authentication happened at the reveal — and it is why a revealed item lands in TextEdit as text rather than as a promised file. Revealed *images* stay on the promise path: the multi-selection drag can only express an image as a file. **Chromium/Electron destinations cannot receive a promised document at all** — WhatsApp accepts the promise and shows the right filename, then reads the file before the post-Touch-ID write happens and ends up with 0 bytes; Finder waits and is fine. That is destination behaviour, not ours: writing earlier would mean decrypting before the drop. Promising a row the user had already revealed was tried as a fix for the mixed case and reverted — it only removed the concrete file URL that does work there.
  - **appkit-multi / file group** — multi-selections and file rows; carries file URLs, Vault promises and joined text together (promise filenames are de-duplicated).
  - **plain-appkit** — any drag that is text only: a text/link row, or a selection of them (`usesPlainAppKitDrag`). It publishes the string and, for formatted text, the RTF `pasteItem` writes, from `ClipboardViewModel.dragFormatting` (`pasteContent ?? richContent`, unsealed for a revealed Vault row; none for links or under *Always paste as plain text*). A selection's RTF is joined by `PasteboardComposer.joinedRTF`, its Vault rows plain, as Copy does. Before this, every drag carried plain text only. A mixed file + text selection (the file-group path) still carries its text plain.
  - **swiftui** — the remaining `.onDrag` fallback.
  - Every path also writes the row's UUID under `AppConstants.reorderPasteboardType`; `ClipboardListView`'s `ReorderDropDelegate` accepts only that type and calls `ClipboardViewModel` to set a midpoint `sortOrder` (`AppConstants.sortOrderStep` gap). `ReorderDragSource.shared` owns the insertion-line state so only one row draws it.
  - What a drag carries is built when it starts, never during a render: the overlay takes `entriesProvider` / `joinedTextProvider` / `vaultPromisePayloadsProvider` closures, and the row decides which overlay to mount from the items' flags alone (`selectionCarriesFilesOrVault`, `contributesDragText`). Deriving the payload in `body` meant stat-ing every selected file and joining the selection's whole text for each of ~60 rows on every selection change, which blocked the main thread long enough to swallow the next click.
- Tunables (polling interval, size cap, expiry purge cadence, previews, blocklisted/password-manager/authenticator bundle IDs, internal pasteboard type) all live in `AppConstants` (`Utilities/Constants.swift`) — change them there, not inline.

## 4. Vault, Sensitivity, Crypto
- `SensitivityDetector`: local regex patterns (cards, IBAN, API keys/tokens, SSH, OTP, passwords, credential pairs, seed phrases, SSN/CNP) + password-manager source detection. Detection is content-only — the app cannot tell which field or page a copy came from. Ambiguous shapes carry a validator (`SensitivePattern.validate`): Luhn for cards, mod-97 + country length for IBANs, the control digit for CNPs. A form password must be one token of 8–64 chars with upper, lower, digit **and** a symbol — the symbol rule is deliberate (keeps `iPhone15Pro2024`-style codes out), so symbol-free passwords are left to the manual lock. The generic `highEntropyString` rule likewise requires at least one digit: without it, a symbol name copied from a debugger (`_NSDetectedLayoutRecursion`) met the three-class test through its underscore and was auto-vaulted. Provider keys with a recognisable prefix have their own patterns and do not depend on the generic one.
- `VaultCryptoManager`: **AES-256-GCM via CryptoKit**, `SealedBox.combined` format. Single `SymmetricKey(.bits256)` stored in the **user Keychain** (`SecItem*`, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, `kSecUseAuthenticationUISkip`) with a synchronized **0600 file backup** in the sandboxed Application Support folder. The query sets no `kSecUseDataProtectionKeychain`, so the item lands in the **file-based login keychain** (`login.keychain-db` — `security find-generic-password -s com.pastespace.clipboard-manager.vault` shows it), which does not enforce the accessibility class (Apple TN3137): user-facing text may say "this Mac only, never synced to iCloud" but must not promise "only while unlocked". The Terms, the Privacy Policy and the README were corrected to say exactly that. No Secure Enclave (it cannot hold AES keys) — the README's marketing copy says otherwise; the code is the source of truth. Do not change the key-storage strategy `[locks-in architecture]`.
- **The protected payload is `content` + `richContent` + `pasteContent`, and `documentText` is dropped outright.** A formatted row's RTF spells out the same words as its content, so `toggleVault` encrypts all three and decrypts all three (`ClipboardViewModel.sealedFormatting` / `unsealedFormatting`); a copy that fails to encrypt is dropped, never stored in the clear. `unsealedFormatting` returns undecryptable bytes unchanged — that is the compatibility path for items vaulted before this, which `sealLegacyVaultFormatting()` also seals once at launch (decryption is the "already sealed?" test, so the sweep is idempotent). Anything reading those columns for a vault row must unseal first: `pasteItem` does, and so does `revealedCopy(of:content:)`, the unprotected twin handed to Quick Look after authentication, so a protected formatted item reads as it was captured. Share and `PasteboardComposer` deliberately use revealed plain text instead. `Equatable`-style nil checks (`hasRichText`, the rich-text icon) stay valid either way. A locked row is findable **only by what it shows**, which is nothing: its FTS `searchText` is empty. Indexing `vaultLabel` put a protected file's full path in the index while the row masked that same name on screen, and indexing `ocrText` let anyone confirm the words inside a protected image by typing them, with no authentication at all. `sourceAppName` — the other FTS column, and metadata the row displays — stays. `ocrText` is sealed alongside `documentText`, `updateOCRText` refuses to write to a locked row, and `sealLegacyVaultFormatting()` seals both columns for rows locked before this. `clearVaultSearchIndex()` then empties **every** locked row's index entry at launch, unconditionally: the sweep only rewrites rows it actually seals, so a row locked by an older build with nothing left to seal would otherwise keep the entry that build wrote.
- Vaulting **seals** `documentText` rather than dropping it: `sealedText` / `unsealedText` wrap the same AES-GCM as the blobs, base64 because the column is text. Dropping it was the first design, and it meant every reveal and every un-vault read the document again — seconds of Vision per scanned PDF, repeatedly, for text the app already had. The sealed value never reaches the FTS index (a vault row indexes only its label and `ocrText`), so search still cannot see inside a locked document. `revealedDocumentText(for:)` decrypts it for the Quick Look panel and only falls back to re-reading the file when the row has none — a row vaulted before this, or captured straight into the Vault. Re-extraction on un-vault is likewise conditional, and OCR is not re-run for an image that already has `ocrText`, which survives vaulting.
- **What a locked row leaves in the clear, and why each is safe.** The payload is fully sealed; around it the row keeps descriptive metadata — source app, times, size, pinned, `kind`, a preview in `vaultLabel`, and `contentHash`. Two of those used to undermine the encryption and are fixed:
  - **The preview is `SensitivityDetector.maskSecret(_:category:)`**, decided by what the value is: dots only for passwords and personal IDs, `•••• 4242` for a card, country code plus the last four for an IBAN, and at most a quarter of the first line (split start/end, nothing under 12 characters) for everything else. Always eight dots, so the preview does not reveal length. The old `maskText` showed the first and last four characters — 8 of a 9-character password on screen — and survives only for masking locked *file names* in the row.
  - **A locked row's `contentHash` is `VaultCryptoManager.keyedHash`**: HMAC-SHA256 under an HKDF subkey of the vault key, prefixed `k:`. A plain SHA-256 stands in for the secret whenever it can be guessed — with the old preview's first and last four digits a card number fell to about 10⁷ guesses. Both digests hash `ClipboardItem.hashInput` (content plus the rich-text byte), so deduplication means the same thing either way. `toggleVault` swaps the digest with the protection. At capture, a locked copy is stored under its keyed digest and may merge **only** into another locked row; an ordinary copy also looks for a locked row holding the same content (`upsertItem(_:matchingHashes:)`), so copying a locked secret again refreshes it instead of adding a readable copy — and the upsert never writes `richContent`/`pasteContent` into a locked row, where a plaintext re-copy would otherwise have put the formatting back in the clear. The reverse case is a **re-lock**: when a capture is locked and a *readable* row holds the same content — a secret the user unlocked earlier — `handleNewItem` locks that row again (`readableItem(contentHash:)`, then the shared `lock(_:in:)` behind the 🔒 button) before upserting, so the copy merges into it: one item, its whole copy history, protected. Keeping both left the password in plain text beside a locked duplicate with its own count. If the re-lock fails, the new copy is still stored locked on its own. The keyed digest is computed only when something could match it (a locked capture, or `vaultCount > 0`). It used to be gated so an ordinary copy would not create the Vault key; since v18 the copy fingerprint does exactly that on the first copy (one login-Keychain item, no prompt — the user's call), so the gate now only saves work. `hardenLockedMetadata()` rewrote rows locked under the old rules once at launch (`vaultMetadataVersion`), decrypting each and dropping the plaintext immediately.
  - Size is left alone: AES-GCM output is exactly the plaintext length plus 28 bytes, so hiding `sizeBytes` would hide nothing. File rows keep `path:` in `vaultLabel` and their bookmark — the file itself sits unencrypted on disk, so the reference is not the secret. And the key's file backup lives in the same container as the database, so these fixes matter when the database file alone gets out, and the preview matters on screen every day.
- **`vaultCount` is counted in the database** (`lockedRowCount()`, refreshed on every reload) — never from `items`, which a search or a filter narrows. Counting `items` read 0 while a free user filtered by Images and let them lock past the free limit.
- `BiometricAuthManager`: fresh `LAContext` per request, `.deviceOwnerAuthentication` (Touch ID with password fallback). Vault items auto-mask after reveal/Quick Look.

## 5. Sandbox & Zero-Telemetry
- Shipping entitlements of the App Store edition (`clipboard_manager/clipboard_manager.entitlements`) are exactly: `app-sandbox`, `files.user-selected.read-write`, `files.bookmarks.app-scope`, `network.client` (**StoreKit only**), `keychain-access-groups` (`$(AppIdentifierPrefix)com.pastespace.clipboard-manager`). `ENABLE_HARDENED_RUNTIME = YES` in both configurations. Never add others. **PasteSpace Business** (`Business/PasteSpaceBusiness.entitlements`) has the same set with `$(AppIdentifierPrefix)com.pastespace.business` as its keychain group; it keeps `network.client` for WebKit (Quick Look's Office/Markdown/CSV previews), not for any connection of its own — it has no StoreKit. The `OCRHelper` service has its own `OCRHelper/OCRHelper.entitlements` with **`app-sandbox` and nothing else** — App Store rules require every embedded executable to be sandboxed, and it needs no capability of its own: no network, no file access (the app hands it an open file handle). Keep it that way.
- `clipboard_manager_adhoc.entitlements` exists **only** for unsigned VM smoke-testing and sets `app-sandbox` to `false`. It is not a second product: never treat behaviour observed under it as sandbox-valid, and never migrate code that only works there into the shipping target.
- No telemetry, analytics, crash reporters, cloud sync, or any non-StoreKit network call. `ITSAppUsesNonExemptEncryption = false` (local-at-rest crypto only).
- **Privacy manifests — one per bundle.** Neither declares collected data (`NSPrivacyCollectedDataTypes` is empty): Apple's "collect" means sent off the device, and PasteSpace sends nothing — two entries that said otherwise (other user content, purchase history) were removed for 3.0 so the manifest, the App Store privacy label and the Privacy Policy agree. `clipboard_manager/PrivacyInfo.xcprivacy` declares UserDefaults (`CA92.1`) and file timestamps/metadata with `C617.1` (the app's own files — `AppDelegate` reads its executable's date to detect a new build), `3B52.1` (files the user copied: sizes in `ClipboardEngine` and the row, `fstat` in `FileWatcher`) and `DDA9.1` (metadata shown to the user: the ⓘ's sizes and file-event dates). The `OCRHelper` XPC service has its own `OCRHelper/PrivacyInfo.xcprivacy` (`fstat` of the file handle it is given, `3B52.1`) — App Store Connect checks every binary in the bundle. Any new required-reason API (file timestamps, disk space, system boot time, active keyboards, UserDefaults) must be declared in the manifest of the bundle that calls it before an upload.
- **`PasteSpaceProducts.storekit` is test-only.** The scheme's Run action uses it for local StoreKit testing; a membership exception on the `clipboard_manager` synchronized group keeps it out of the app's Resources, where the synchronized folder used to copy it into every release. The effective `LSApplicationCategoryType` is the build setting (`public.app-category.productivity`); `Info.plist` no longer carries a second, conflicting value.
- **The review reminder is the second sanctioned StoreKit interaction** (`Utilities/ReviewPromptManager.swift`), and adds no entitlement. `AppStore.requestReview(in:)` is macOS 13+, so no `#available` gate at the 14.0 target; `SKStoreReviewController` is deprecated from 15.0 and unused. It needs an `NSViewController` in a key-capable window, so `AppDelegate` assigns the panel's `ZeroSafeAreaHostingView` through `panel.contentViewController` instead of `panel.contentView` — equivalent for the window, and it gives StoreKit a controller without touching the SwiftUI tree. Parking a spare `NSView` inside the hosting view was the first attempt and AppKit rejects it ("Adding 'NSView' as a subview of NSHostingView is not supported"). Apple reports nothing about the request either way (`requestReview` returns `Void`), it is documented as having no effect in TestFlight, and it **fails outright under a StoreKit configuration file** (`storekitagent.ReviewManager.ReviewError Code=3`, `client-environment-type=XcodeTest`) — so a Debug run with the scheme's StoreKit Configuration set shows nothing, whatever the gate says.
- **The gate is offline and one-directional.** Every criterion in `AppConstants.Review` is a count of what PasteSpace did — pastes, distinct active days, features reached (a `Milestone` bitmask), plus cool-offs after a user-visible failure (`recordProblem`, from `showFileError`) and after the modal Pro paywall (`recordPaywallShown`, from `presentProUpgradeWindow` only — the always-present upsell inside Settings is furniture, not a pitch). `armIfEligible()` runs once per launch after `preloadItems()`; the ask itself waits for the panel to reopen after a paste, with nothing else on screen (`AppDelegate.maybePresentReviewPrompt`). **Whether a review was left is unknowable** — no API reports it, and asking Apple would mean per-user tracking — so `engagedAt` records only that the user *pressed a Rate button*, and pressing it stops reminders permanently. Do not "improve" any of these keys into something that tracks the user's App Store activity.
- Settings ends with a **permanent** "Rate PasteSpace on the App Store" card (`SettingsView.rateOnAppStoreCard`, last in the scrolling content, below the Pro upsell — title above, five stars under it), which must not be hidden after use: reviews get updated, and an affordance that vanished on an unverifiable guess would strand the user who wants to re-rate after a fix. Its five stars are **one button**, not five ratings — nothing we draw can submit anything, and routing high ratings to the App Store while catching low ones in our own UI is against App Store guidelines. It is disabled (with a `.help` saying why) while `AppConstants.Review.appStoreID` is the placeholder, and `openReviewPage()` deliberately checks that *before* recording engagement so an inert button cannot silence future reminders. `appStoreID` is **6762815491** — the "Apple ID" in App Store Connect → App Information, the `id…` in the store URL, verified against Apple's public lookup (`itunes.apple.com/lookup?id=6762815491` → `com.pastespace.clipboard-manager`).
- In DEBUG, Settings carries a review workbench beside the Pro one: presenter (System / Mock / Off), "Show now" (presents without spending one of the three lifetime asks), a live criteria read-out naming the first blocking condition, and Fast-forward / Reset. The **mock** sheet travels the identical path — same host controller, same window, same timing — and exists so the surrounding behaviour can be tuned without spending Apple's three-per-year cap on this Mac.
- File items: always store `URL.bookmarkData(options: .withSecurityScope)` and resolve with `startAccessingSecurityScopedResource()`; never persist raw paths as the source of truth.
- **Files & Folders prompts (macOS 27).** The first time a file copied from the Desktop, Documents or Downloads (or a removable/network volume, or cloud storage) is opened — at capture that is `bookmarkData` in `ClipboardEngine` — macOS asks "PasteSpace would like to access files in your … folder", once per location, remembered under System Settings › Privacy & Security › Files & Folders. The request comes from `sandboxd`, and the unchanged App Store build raised it too: it is the system, not a regression. The clipboard does hand PasteSpace a sandbox extension for the copied file — verified with a sandboxed probe, for `string(forType: "public.file-url")` and `readObjects(forClasses: [NSURL.self])` alike, so reading the URL differently changes nothing — but on 27 that extension no longer exempts these locations. `Info.plist` carries a purpose string for each (`NSDesktopFolderUsageDescription` … `NSFileProviderDomainUsageDescription`), which is the prompt's only explanation line; keep them true to what the app does with a copied file (it only reads it). **After "Don't Allow"** the item is still stored — path, name, size (metadata stays readable) — but without a bookmark, and nothing can be read from it: no preview, no extracted text, no OCR. `ClipboardItem.lacksFileAccess` (a single file with no bookmark) names that state, and everything keys off it: `FileStatusStore` reports `.noAccess` ("PasteSpace isn't allowed to open it", a raised hand, no strike-through — like a disconnected disk, no verdict on the file) unless `stat` says `ENOENT`, because without a bookmark the sandbox answers for the path only in the run that captured it and refuses it, existing or not, ever after — before this the row read that refusal as "File no longer exists"; the row's buttons gate on it like any other absence, with `ClipboardItem.noFileAccessExplanation` (where to allow the folder, then copy again) as the tooltip; Paste and Share refuse with the same explanation instead of "no longer exists"; and `FileWatcher` does not follow such files at all, since a path visible in the capturing run and refused in the next would have been recorded as a permanent deletion. **Recovery is copying the file again** once the folder is allowed: `upsertItem` now takes the new copy's bookmark when it merges (it used to keep only the old row's, so the row stayed without access forever), the row's status task is keyed on having a bookmark, and the merged row gets its document text and OCR because both were left unrecorded. Group members without a bookmark still count as missing in the group's tally.
- Reject any request for `Process()`, shell scripts, AppleScript, `CGEventTap`, private APIs, or extra entitlements — explain and offer a sandbox-safe alternative.

## 6. Local Engines
- OCR: `OCRService` with Vision `VNRecognizeTextRequest`, wrapped in `ProcessInfo.beginActivity(.userInitiated, .idleSystemSleepDisabled)`; downscale via ImageIO only when the image exceeds the max dimension. **No size limit on the image** (there was a 5 MB one on the bytes, which left bigger photos and scans unrecognised): ImageIO decodes straight to at most 4096 px, which is what bounds the cost. Image *files* go through `recognizeText(fromFileAt:)`, decoded from disk under the bookmark's scope (`ClipboardViewModel.OCRSource`) and never read into memory first. Images skipped under the old limit are recognised when copied again; there is no OCR backfill. Result is written to DB then propagated to `items` via `refreshAfterOCR` + `ocrCompletionCount`.
- **Recognition runs in the `OCRHelper` XPC service, and only falls back to the app.** Vision's models are ~110 MB and stay resident in whichever process first used them — measured, the app's footprint went from 25 to 137 MB after one recognition and never came back. App code calls `TextRecognizer` (`Domain/Services/TextRecognizer.swift`), never `OCRService` directly: it sends the work to the helper over `OCRHelperProtocol` — image bytes, or for an image file an open `FileHandle` the app opened under the bookmark's scope (the helper has no file access and memory-maps the descriptor) — and the helper runs the same `OCRService`. The helper quits after 30 idle seconds (`IdleExit` in `OCRHelper/OCRHelperService.swift`, counting requests in flight so it never quits mid-recognition), taking the models with it; the connection survives as *interrupted*, and the next request relaunches it in ~0.3 s. **Recognition never depends on the helper**: anything that stops it answering — not embedded, failing to launch, crashing mid-request — makes `TextRecognizer` run `OCRService` in-process, the path the app always had, so the only cost of a missing helper is memory. A connection that is *invalidated* (the helper can't be launched at all) is not retried until the next launch. Vision's own errors come back through the reply and are not treated as the helper failing. The helper runs each request at `.utility`, the priority the app gives the same work (at `.userInitiated` it waited on ImageIO's default-QoS decode threads, a priority inversion Xcode reports). **`perform` is synchronous and its results are read after it returns — never resume a continuation from a request's completion handler**: Vision reports a failure twice (the handler *and* a throw), and that double resume was a fatal error that killed the helper and then the app at every recognition wherever Vision couldn't load its models. That place exists: in a macOS 27 VM (paravirtual GPU, no Neural Engine) every `.accurate` configuration fails at once — any revision, CPU only, the Swift `RecognizeTextRequest` — and Live Text itself reads nothing, while `.fast` works; so `OCRService` retries with `.fast` (default languages) when `.accurate` throws. `OCRService` lives in `Shared/` and logs through `Logger.ocr`, which each target defines — the helper's under its own subsystem.
- **`MemoryRelief.afterHeavyWork()`** (`Utilities/MemoryRelief.swift`) calls `malloc_zone_pressure_relief` two seconds after the last heavy job — OCR, document extraction, a Quick Look panel closing — so memory already freed is handed back to macOS instead of sitting in the allocator until memory pressure (97 MB of a 310 MB footprint was exactly that). A burst of jobs asks once, after the last. **It only does anything on macOS 14–15**: macOS 26's allocator implements the call as a no-op (measured on 26.6.2: it returned 0 and released nothing, from 64-byte blocks to 1 MB ones) and leaves freed memory to the kernel to reclaim under pressure, with no public way to ask sooner. So on 26 the drop in footprint comes from the `OCRHelper` alone; do not read a missing "Returned …" log line as a bug. On macOS 27 the call hands back amounts under a megabyte, so the line prints a byte count (it printed "Returned 0 MB" while it counted whole megabytes). It frees nothing in use and changes no behaviour; call it from new heavy paths with a `defer` at the start of the detached task.
- Data Magic: currently **57** `Transformation` structs registered in `DataMagicEngine.allTransformers` (array order = display order; the array is the source of truth, not this count). `DataTypeDetector.detect` picks applicable ones, computed on demand when the user taps 🪄 — never on capture. Pure Swift / Foundation coders only.
- **Relevance is the point.** `DataMagicEngine.sections(for:)` splits results into actions specific to the detected content and generic `textToolIDs`, which the popover collapses under "Text tools". `allowedTextTools(for:)` decides which generic ones are worth offering per type — code keeps the two escapes, a link keeps URL encoding, an email keeps lowercase, a table/colour/date keeps none, prose keeps all. Every action's `canTransform` must also be conditional on the content actually needing it (no "Remove Tracking" without tracking parameters, no "Join into One Line" on commented code, no "Sort Lines" on a table).
- **Document text** (`Domain/Services/DocumentTextExtractor.swift`, Pro-only via `Feature.documentSearch`) comes back in **two forms**: plain text for the FTS index, and the document's own formatting as RTF in `documentRichText` (v13, sealed for Vault rows like every other formatted copy). `PDFPage.attributedString` carries a PDF's real fonts, sizes and colours, and the AppKit importers already produce an attributed string — it used to be discarded by calling `.string`. Both readers stand each picture in the text as an attachment on an object-replacement character (U+FFFC), and `withoutAttachments` removes them before anything is stored: a PDF with 27 images put 27 invisible characters into the searchable and copied text, and the RTF writer tried to encode each picture and failed ("CGImageDestinationFinalize failed", 27 times) — PasteSpace keeps words and their formatting, never pictures. Text read before this keeps its U+FFFC characters, which the FTS tokenizer treats as separators. `rtf(from:)` returns nil when the text is uniform, so a `.txt` or a single-font PDF stays plain rather than gaining a pointless "Copy formatted". **Vision returns no formatting at all** — strings, boxes and confidence — so recognised text from an image or a scanned PDF is plain by nature, and keeps the single `Copy` button. PDFKit page by page for PDFs, AppKit's importers for RTF/RTFD/DOC/DOCX/ODT, **`SpreadsheetTextReader` for Excel workbooks (`.xlsx`, `.xlsm`)**, `HTMLTextReader` for HTML and web archives, and the first bytes of text and source files. Workbooks were silently unread until 3.0 — no importer claimed them, so they fell through to "not a document we read" and were stored as empty. macOS has no spreadsheet importer, so `SpreadsheetTextReader` reads the format itself with system frameworks only: the zip's central directory (stored and DEFLATE entries; ZIP64 reports unreadable), raw DEFLATE through the Compression framework (`COMPRESSION_ZLIB`, streamed, no part inflated past 32 MB for shared strings or 16 MB per sheet — a zip-bomb bound), and `XMLParser` over `xl/sharedStrings.xml` (`<rPh>` phonetic guides skipped), `xl/workbook.xml` + its rels for sheet order and names (chart sheets left out; falls back to `xl/worksheets/sheet*.xml` in number order), and each sheet — namespace prefixes such as `x:c` stripped, a line per row, a tab between cells with up to eight for empty columns, values as stored (a date is Excel's day number, a formula its cached result), stopping at the character cap (a 300,000-row workbook: 0.3 s, 54 MB peak). Plain text only — a sheet's look lives in its styles. It returns nil when the file can't be opened (`.unsupported`, tried again later) and "" for a non-zip such as a password-protected workbook (recorded as read). `.xls`, Numbers and ODS are not read. `rereadWorkbooksOnce` (`workbookRereadVersion`) marked workbooks stored empty before 3.0 as unread, once, for the ordinary backfill to pick up. **What is read is capped, never whether: there is no file-size limit, at the user's explicit request** — 200 K characters and 100 pages (`AppConstants`) bound the work, so a document is never skipped for being big — a 4,444-page manual is 8.7 M characters and 7 s read whole, 300 ms for the first hundred pages. The 25 MB limit on non-PDF files that used to stand in for that is gone, and must not come back; it was also no protection: **nothing in extraction may run on the main thread.** AppKit's importers ran on the main actor, where a DOCX of 1 MB holding 26 M characters took 8 s; only the *HTML* importer actually needs the main thread, so the others now run where they are called (off main), and HTML never reaches AppKit at all. AppKit's HTML importer is WebKit and is synchronous on the main thread — 3 s for a 3 MB page and 36 s for 30 MB, with not one timer firing — so **`HTMLTextReader`** (`Domain/Services`) reads HTML itself: one pass over the bytes (memory-mapped; UTF-8 read in place, any other `charset` converted once), stopping at the character cap, 0.07 s for the same 30 MB. It skips `script`/`style`/`title`/`svg`…, decodes HTML 4's named entities plus numeric ones, applies HTML's implied end tags (`<p>`, `<li>`, cells, rows) so the element stack stays shallow, and never loads anything a page refers to (AppKit's importer did not fetch either; checked against a local server). Its word set matches WebKit's on real pages (502/502, 2,910/2,910, 2,118/2,127). **Formatting comes from the page's CSS** (`HTMLStyleSheet.swift`): `<style>` blocks and `data:` stylesheet links gathered in document order before the pass, a web archive's saved `text/css` subresources, `style` attributes and HTML's presentational attributes (`<font>`, `align`, `bgcolor`), cascaded by specificity, source order and `!important`. Selectors: type, class, id, `*`, attribute tests, descendant and child combinators, `:root`, `:link`, `:first-child`, `:nth-child()`, `:first-of-type`, `:nth-of-type()` — anything needing what comes later (`:last-child`, siblings) or interaction (`:hover`) drops the whole selector rather than matching loosely. Custom properties and `var()`, `calc()`/`min()`/`max()`/`clamp()`, every length unit with `rem` against the root's own size. **The target is AppKit's import — what PasteSpace showed before**, measured against it word by word (a CSS test page 79/79 identical, TrustStore 10,537/10,537): one CSS pixel is one point and `medium` is 12, generic monospace is Courier 13, links default to #0000EE underlined (their own CSS can remove that, an ancestor's decoration can't be removed), black is left unwritten, `@media` is evaluated for an 800 × 600 landscape screen with a fine pointer, and only `display: none` removes text (`visibility: hidden` hides collapsed menus whose text is content; the import kept it). Deliberate departures: the colour scheme is always **light** (the import follows the Mac's appearance, which put dark-theme pale text into copies), the system font is written as Helvetica Neue and `ui-monospace` as Menlo (`.AppleSystemUIFont` and SF Mono cannot be opened by other apps), and backgrounds follow the import's split — a `<div>`/`<p>`/`<li>`/inline element's background goes behind its text, while `<body>` and table parts' (which the import draws as page or cell backgrounds) do only when the text is too pale to read on white. Weights stay numeric and pick the family's nearest face the way CSS does (CoreText; `NSFontManager` is main-thread only). Cost: 0.13 s / 56 MB for a 30 MB page, 0.44 s / 60 MB for 30 MB under 5,000 rules. A web archive is a property list; only its `WebMainResource` is read, with the encoding it declares. Plain text reads `documentTextMaxCharacters × 4` bytes and decodes them with **`TextEncodingDetector`** (`Domain/Services`): byte-order mark, then unmarked UTF-16 (before UTF-8 — Latin text in UTF-16 is also valid UTF-8, full of NULs), then UTF-8 with up to three trailing bytes dropped, then macOS's `NSString.stringEncoding(for:)` on the first 64 KB cut at its last line feed (no character in any of those encodings contains 0x0A) — deciding on the whole 800 KB read took 0.55–0.86 s, the 64 KB probe 0.09–0.12 s — with the whole read then decoded in that encoding, then Latin-1. The detection is given **no hint** — suggesting the user's languages made a Russian Windows-1251 file decode as Romanian Windows-1250 — and a Cyrillic answer is re-checked against its siblings (`bestCyrillic`: fewest mid-word capitals and foreign Cyrillic letters), because macOS misreads KOI8-R. Verified on 28 samples (Windows-1250/1251/1252/1253/1254/1256, ISO-8859-2/5/16, KOI8-R/U, CP866, CP874, Shift-JIS, EUC-JP, GB18030, Big5, EUC-KR, UTF-8/16/32 with and without marks, a truncated Shift-JIS read); old Mac Roman is the known miss. `HTMLTextReader` uses the same detection for a page that names no charset and whose first 64 KB aren't UTF-8. A PDF with no text layer is rendered through CoreGraphics (never `PDFPage.thumbnail`, which would force the main actor — `PDFPage` is not `Sendable`) and read by `TextRecognizer` **page after page with no page limit**, until the character cap — at the user's request; it used to stop after five pages. That is a second or two of Vision per page, so the launch backfill now awaits each document before starting the next (`extractDocumentText` returns its task) instead of launching fifty at once, and the Vault reveal path, which Quick Look waits on, passes `recognizingScans: false` and lets the panel show the file's own preview. Scans read under the old five-page limit get a **one-time re-read** (`rescanDocumentsReadUnderPageLimit`, after the backfill in `backfillDocumentText`): nothing stored distinguishes a recognised scan from a single-font PDF, so it re-reads every unlocked PDF whose text is plain or empty (`documentsToRescan`: `documentRichText` is the empty marker) — milliseconds for a text layer, every page for a scan — 50 per launch, walking rowids up to the highest rowid when the pass began (saved in `documentRescanEnd`, so later captures, already read without the limit, aren't redone), with the position saved after each document (`documentRescanCursor`) so a quit resumes there; `documentRescanVersion` marks it done. `isBackfillingDocuments` keeps launch maintenance and a Pro activation from running two passes at once. Extraction is switchable in Settings (`SettingsManager.documentTextEnabled`, "Text extraction from documents", beside "Text recognition in images (OCR)") and gated at all three entry points — capture, launch backfill and reveal. Turning it off stops new reads; text already extracted stays and remains searchable. Extraction runs after capture like OCR, plus a capped backfill at launch (`backfillDocumentText`); the result lands in `documentText`, which `extractSearchText` folds into the FTS index so search reaches inside documents. `NULL` means "not read yet" and `""` means "read, nothing there" — that difference is what stops the backfill retrying forever. `documentRichText` carries the same three states as a blob: nil never looked, **empty** looked and found none (a plain file, or Vision's output), non-empty is the RTF — read it through `ClipboardItem.documentFormatting`, which collapses the marker. The backfill takes rows that were never read *and* rows read before formatting was kept (`documentText <> '' AND documentRichText IS NULL`), so an older history upgrades itself 50 documents per launch; a scanned PDF among them is recognised once more and then marked, never again.
- Code detection comes from `CodeLanguageDetector` (`Domain/Services`): ~30 languages by syntax plus JSON/HTML/XML/YAML by parsing, shared with the row's ⓘ so both name content identically. `DataTypeDetector` returns `.codeBlock` from it and defers HTML fragments to `isHTML`. Keep its regexes free of nested repetition and its sample bounded — it runs on the main thread. There is a scratch corpus approach for it: compile the detector standalone and run snippets/prose through `describe` before changing rules.

## 7. Persistence & Monetization
- **GRDB.swift with `DatabaseQueue`** (serialized; no `DatabasePool`), SQLite in Application Support, **FTS5** table (`clipboardItem_fts`, external-content) kept in sync **manually on every insert/update/delete path** in `DatabaseManager` — a new write path must add its own FTS maintenance. Ordered migrations `v1_…` → `v20_addFileEvents`: always append a new `registerMigration`, never edit existing ones `[locks-in architecture]`.
- **Image bytes never live in the list.** Images have no size limit (copied as image data or as files), so their bytes stay out of `items`: `DatabaseManager.listSelection` replaces `content` with `X''` for every image `contentType` the history holds (read from the `contentType` index) in both list queries, and `toDomainModel(database:)` gives such an item a `DeferredContent` — `ClipboardItem.content` is now a computed property that reads the row's bytes back (`storedContent(id:)`, synchronous and reentrant) the moment paste, drag, Share, Quick Look or the Vault ask, so none of those call sites changed. `database:` is a required argument so no conversion can silently produce an image with no bytes; pass nil only for a row read whole. A deferred item takes `contentHash`/`sizeBytes` from the row (`storedHash`/`storedSize`) instead of hashing bytes it doesn't have. The last four reads are cached (`DeferredContent`, 256 MB cap) keyed by id **and** digest, so one action reading twice reads once and a row locked or unlocked underneath can never be answered with its old bytes; `toggleVault` clears that cache on every lock so a readable copy doesn't outlive it. **Never read `content` to draw a row** — for an image that is a database read per frame on the main thread. The row's "1920 × 1080 · 240 KB" comes from `ImageSummaryStore`: read when the row appears, on a serial background queue (one image in memory at a time, cancelled if the row leaves first), header only, cached as text. **v17 moved `content` to the last column** — SQLite reads a row's columns in order, so with `content` second every list query walked each image's overflow pages to reach the columns after it: 125 ms for twenty 50 MB images even with `content` left out, 0.1 ms once it is last; reading one 50 MB image on demand is ~7 ms. The rebuild (create, copy with explicit rowids — the contentless FTS index is keyed by them — drop, rename, recreate the ten indexes) relies on GRDB running migrations with foreign keys off, so dropping the old table does not cascade into `copyEvent`; it was rehearsed on a copy of a live database (rows, rowids, digests, sizes, copy events and FTS results identical; integrity and FK checks clean). Text is still loaded whole by the list, which is why `maxItemSizeBytes` (10 MB) now applies to text alone. Launch maintenance VACUUMs only when the free pages exceed max(5 MB, a quarter of the file) (`reclaimableBytes`) — it used to rewrite the whole file on every launch once it passed 5 MB.
- **Quick Look versions.** Saving in the Quick Look editor never overwrites: it force-inserts a new item (`sourceAppName == ClipboardItem.quickLookEditSourceName`, `isQuickLookEdit`) that also stores a snapshot of the *first captured* version (`original*` columns, v10) and the root item's ID (`originalItemID`, v11) — editing an edit carries both forward, so a family stays flat. `ClipboardViewModel.quickLookFamily(of:)` builds original + edits (oldest first = Version 1…n); Quick Look shows `Original | Edited · x of y` (`QuickLookVersionStrip`) in view mode, opening on the clicked version. The real original is preferred over the snapshot; the snapshot is read-only. Vault items get no snapshot, and vaulting an edit clears its snapshot and link. "Show in History" hides for the highlighted row, mirrored from `selectedIndex` via `QuickLookManager.shared.historyFocus`.
- **Document Quick Look.** A file row whose `documentText` is non-empty opens `DocumentPreviewView` — our own panel with two tabs, the system preview (an embedded `QLPreviewView`) and the extracted text. The text tab is the same `RichTextPreviewView` an image's recognised text gets: selectable and editable, saved as a new history entry, with the version strip and Show in History. It opens on `documentRichText` when the document had formatting, which is what makes `wasOriginallyPlain` false and brings out `Copy formatted` beside `Copy as plain text` — the labels already keyed off `canCopyFormatted`. The floating selection popover follows the same rule: two buttons over formatted text, the single `Copy selection` over plain. There is no copy-everything button by design. Any other file keeps the plain `QLPreviewPanel` path. **Web pages and web archives get no Preview tab** (`showsFilePreview`, from `QuickLookManager.isWebDocument`): `QLPreviewView` draws HTML with WebKit in a separate process that wants read access to the file's whole folder, which a sandboxed app — holding the file alone — can't grant, so the tab stayed blank behind a wall of `WebContent` sandbox errors ("Ignoring request to load this main resource because it is outside the sandbox"). A `WKWebView` of our own was rejected: it fetches what a page links to unless every network path (subresources, preconnect, DNS prefetch, scripts) is shut, not a basis for the offline promise. The panel shows the extracted text alone, which `HTMLTextReader` formats from the page's CSS. An **image** with `ocrText` is laid out the same way by `ImagePreviewView` — Preview and Extracted text as tabs rather than the text stacked under a shrinking thumbnail. Its text tab is the full `RichTextPreviewView`, so recognised text can still be edited and saved as a new item; both tabs stay mounted so switching never discards an edit in progress. It also carries the version strip: `QuickLookManager.makeVersions(for:family:)` builds `Original | Edited · x of y` for every panel, taking the original's text from `fullText ?? ocrText ?? documentText` so an image or a document can be the root of a family. `originalVersion(forEditOf:)` stores that recognised text as the edit's snapshot and the image's id as `originalItemID`, which is what makes the family — and "Show in History" — work for images the same way it does for text. The panel holds the row's security-scoped grant for as long as it is open (`documentPanelScopes`) and gives it back on close.
- **Find in Quick Look** (`UI/Views/QuickLookFind.swift`). Every panel that shows text — a text item, an image's recognised text, a document's extracted text — has a magnifying glass at the right of its title bar (an `NSTitlebarAccessoryViewController`, `.trailing`: the one spot every panel has in both modes and on either tab), and ⌘F opens the same bar above the text, in view mode and in the editor. Return / ⌘G go forward, ⇧Return / ⇧⌘G back, Esc or Done closes. `TextFindController` belongs to the **panel**, not the view: `QuickLookPanel`, the `NSPanel` subclass every SwiftUI Quick Look panel now is, holds it and answers ⌘F/⌘G/⇧⌘G in `performKeyEquivalent` before any view sees them — that is what lets ⌘F work on a document's Preview tab, where `QLPreviewView` has the focus. Asking for find brings the text tab forward and leaving the tab closes find (`quickLookFindFollowsTab`), so the glass never lights up over a bar that is out of sight. The find bar has a single slot in `RichTextPreviewView` for both modes; giving each mode its own made Edit build a new bar, whose `onAppear` took the cursor back from the editor. Matching is case- and **diacritic**-insensitive (`sarbatoare` finds `sărbătoare`), capped at `maxMatches` (10,000). Matches are drawn with the layout manager's **temporary attributes**, which live outside the text storage, so they never reach the saved RTF, the undo stack or a copy — and that is why both Quick Look RTF views are now created on TextKit 1 (`usingTextLayoutManager: false`): `NSTextView()` is TextKit 2 since macOS 13, and this file already read `layoutManager` (selection popover, editor), which silently switched each view to TextKit 1 at its first selection. The text views `attach`/`detach` themselves, so switching modes re-targets find. Edits re-search through `NSTextStorage.didProcessEditingNotification` (character edits only), keep the current match and never scroll — the user is typing. Changing the query anchors on the current match, so refining a query stays in place. Closing find selects the current match (the editor's cursor lands on it) unless the user has moved the selection since it was shown, and ⌘G after such a move continues from the user's cursor, as TextEdit does. The query never touches the system find pasteboard, which every app can read — a search inside a revealed Vault item would otherwise leave it there. `SelectableRTFView` now reloads only when its RTF changes (`Coordinator.loadedRTF`): it used to compare against RTF re-serialised from the display-adapted storage, which never matched, so every render of the panel replaced the text and wiped the selection and the highlights.
- **The selection's copy button must be taken down by whoever removes its text.** `CopySelectionCoordinator` shows `Copy selection` (or the formatted pair) as a borderless child window of the Quick Look panel, and the panel keeps its children on screen: when Edit or Exit swapped the text view, the coordinator went away with the button still up, over the editor, until it was clicked — and the next selection made a new one beside it. `dismissCopyPopover()` is the only way down (detach from the parent, then order out; an ordered-out child is still a child). Both RTF views call it from `dismantleNSView`, and from `updateNSView` while `isOnScreen` is false — `RichTextPreviewView` receives that from the tabbed panels (`tab == .text`), whose hidden tab otherwise left the button floating over the file's preview. Any new text view that uses the coordinator needs the same two calls. **Copying a selection writes the clipboard and nothing else**: both buttons put the internal marker on the pasteboard (so the engine skips it) and never call `onCopySelection`, which saves a new history item. They used to, and every copied fragment — from a text item, a document's extracted text or an image's recognised text, in view mode or in the editor — landed in history as a "Quick Look Selection". Only Save adds a version; the panel's own `Copy formatted` / `Copy as plain text` / `Copy edited` are clipboard-only too.
- **One query builds the list.** `fetchItems(matching:sort:query:limit:)` composes text, criteria and order together; `fetchItems(limit:)` and `searchItems(query:limit:)` are thin wrappers over it, so the ordering expression and the FTS quoting each exist once. It joins `clipboardItem_fts` only when there is text to match. `ItemFilter` / `ItemSort` / `ItemKind` live in `Domain/Models/ItemFilter.swift`. **A filter may only use what a row is willing to show** — the same rule as the Vault search policy — which is why `hasExtractedText` carries `isVault = 0`: that badge is never drawn while locked. Every sort but `.custom` is a lens: `sortOrder` is never rewritten to match one, and manual reordering is disabled while one is active (`ItemSort.allowsReorder`).
- **Copy history (v16).** Every copy is a row in `copyEvent` (`itemID` → `clipboardItem.id` with `ON DELETE CASCADE` — GRDB enables foreign keys by default — so deletion, the history limit, retention and Ephemeral Mode need nothing of their own): `origin` `app` with the source app's name, written inside `upsertItem` for both a new capture and a merge, or `pastespace` with how (`CopyEvent.PasteSpaceDetail`: nil, plain text, extracted text, Data Magic), written by `recordCopies`, which never moves the row. Quick Look saves force-insert and are not copies, so they log nothing. `DatabaseManager.logCopy` inserts only `WHERE EXISTS` the item, so a row deleted mid-write records nothing instead of failing on its foreign key. Existing rows were seeded with the two copies the database already knew (`timestamp` in the source app, `lastUsedAt` from PasteSpace) and marked `seeded`; `CopyHistory.startsPartway` makes the ⓘ say "Earlier copies weren't recorded" rather than show a count that looks complete. The ⓘ (`ClipboardRowView.copyHistoryLines`) shows `Copied: N times` and the newest 20 records, reloading on every open; a locked, unrevealed item stops at "Protected", so its history appears only once revealed. Drags and Share are not recorded.
- **Copy history outlives the item (v18, v19).** At the user's request, deleting an item no longer resets its copy history when the same content is copied again — for every deletion path, Clear history and Ephemeral Mode included (the user's call: the fingerprint reveals nothing, so Ephemeral's promise holds), and for locked items too. Each row has a **copy fingerprint** in its own table, `copyFingerprint` (`itemID` → item, cascade), not a column: `ALTER TABLE ADD COLUMN` would land after `content`, undoing v17. `VaultCryptoManager.copyFingerprint(ofPlainDigest:)` is HMAC-SHA256 of the **plain** `contentHash` under its own HKDF subkey of the vault key (`com.pastespace.copy-tally.v1`, prefix `c:`) — keyed because a plain digest of deleted content would let anyone holding the database confirm guesses of it; from the plain digest so locking and unlocking never change it and an unlocked row needs no blob read. Identity is `hashInput`'s, so the same text from any app is one item and a file is its location. The **`copyTally_foldOnDelete` trigger** (`BEFORE DELETE ON clipboardItem`, recreated by v19) adds the row's `copyEvent` count and `seeded` flag into `copyTally` under that fingerprint, copies the records themselves into `deletedCopyEvent` (times, origin, app name or how — never content), and appends an `origin = 'deleted'` marker stamped `strftime('%Y-%m-%d %H:%M:%f','now')`, GRDB's own UTC `Date` format, all before the cascade removes the originals — a trigger rather than code because there are seven delete paths and the next one would forget. **A table rebuild (`DROP TABLE`) does not fire it**; a future v17-style migration must carry `copyFingerprint` across by `id`, which it does as long as ids are preserved. Writers: `upsertItem(_:matchingHashes:copyFingerprint:)` for the row that ends up holding the copy (insert or merge, same transaction) and `forceInsertItem(_:copyFingerprint:)` for Quick Look saves, both `INSERT OR IGNORE … WHERE EXISTS`; `backfillCopyFingerprints()` fills any row without one, decrypting locked rows (keyed `contentHash`) to recompute the plain digest — `AppDelegate` awaits it at launch **before** the Ephemeral wipe, which would otherwise delete rows before they were counted. `copyHistory` adds the tally to the total, ORs its `startsPartway`, and returns **three separate lists**, which the ⓘ draws as three sections (the user asked for copies and deletions apart): copies — the item's own records and the fingerprint's non-marker `deletedCopyEvent` rows merged newest first, 20 shown, `unlistedCopies` is the "and N earlier"; "Deleted from PasteSpace history: N times" — the markers, 10 shown, their count being `deletionCount`; and "File on disk" — the fingerprint's `fileEvent` rows (below), 10 shown. v18 kept only the count; v19 keeps the records because the user wanted the dates and apps of copies made before a deletion. **Ephemeral Mode keeps only the count** — the user's choice, since a timeline of when and in which apps things were copied is part of what the mode promises to erase: the launch wipe calls `clearAll`/`clearUnpinned(keepingCopyHistory: false)`, which notes `MAX(id)` of `deletedCopyEvent` before the delete and drops every row above it afterwards, in the same transaction (AUTOINCREMENT, so ids only grow). Every other path — delete, history limit, retention, Clear history, Clear Pinned/Vault — keeps the records. `pruneDeletedCopyHistory` (launch maintenance, so **after** the wipe, which must never find a fingerprint's older records already pruned to make room) keeps the newest 20 copy records and 20 file events per fingerprint with `ROW_NUMBER()`; older copies survive as the count, and markers are never pruned (they are the deletion count, one per deletion). Settings › *History of deleted items* shows how many deleted items have one (`copyTally` rows with `copies > 0`) and **Forget** empties `copyTally` and `deletedCopyEvent` and drops the `fileEvent` rows of items no longer in the history; nothing else deletes from `copyTally`. The Privacy Policy (§3, §6, §12, §14), the Settings caption and the README describe exactly this, Ephemeral's exception included.
- **What happened to a copied file (v20, `Domain/Services/FileWatcher.swift`).** At the user's request the ⓘ also says when a file in the history was moved to the Trash, put back, or deleted permanently (emptied from the Trash, or ⌘⌥⌫). `FileWatcher` (`@MainActor`, started from `ClipboardViewModel.start()` **after** the fingerprint backfill and the Ephemeral wipe, then `sync()`ed after every `reloadItems`) follows the files of the newest 1,000 file items — a group's members each, a locked group's not at all (sealed). **Live:** each file is opened `O_EVTONLY` while its bookmark's scope is held (the descriptor outlives the scope; materialising iCloud-only files is switched off for the `open`, so watching never downloads one) and watched by a `DispatchSource` for `.delete/.rename/.revoke`. The handler — built in a `nonisolated static` func so it carries no main-actor isolation onto the watch queue — reads `fstat` link count and `F_GETPATH` while the descriptor is certainly open: a rename into a path with a `.Trash`/`.Trashes` component is *trashed*, out of one *restored*, anywhere else nothing; an unlink (or failed `fstat`: ejected volume, deleted folder) is looked at again **one second later through the bookmark**, because a safe save replaces the file under the same name (verified: `write(atomically:)` delivers an unlink, then the path holds a file) — still there is no event, gone is *deleted*, unreachable volume is nothing. **Offline:** `fileWatchState` holds the last state per file (cascade with the item); the first look in a run compares with it — a Trash move is dated by the file's `addedToDirectoryDate` (when it arrived in its folder, verified to update on both moves), a deletion only by when it was noticed (`noticedOnly`, shown "deleted permanently (noticed then)"), and a file never seen before that is already gone records nothing. Events live in `fileEvent` under the copy fingerprint (no FK), so they outlive the item like its copies; a group member is stored as its **position**, never its path, so a deleted item leaves no file name behind. `recordFileState` writes nothing for a deleted item or one without a fingerprint. The Ephemeral wipe deletes the wiped items' events before the delete. A file that can't be watched — gone, on a disconnected disk, or not openable — goes into `idle` and is not looked at again until a volume mounts (`NSWorkspace.didMountNotification`) or the next launch; bookmark resolution passes `.withoutMounting`, so a check never mounts a network volume. The process descriptor limit is raised (`setrlimit`) to fit one per watched file. `FileStatusStore` now judges Trash and existence through `FileObservation` (bookmark first when the file isn't at its stored path), so a row whose file was trashed after the copy says "File is in Trash" — before, only a file *copied from* the Trash did. `FileStatus.presence` is `.available`, `.inTrash`, `.gone` or `.diskMissing` ("Its disk isn't connected", no strike-through — an unplugged drive is no verdict on the file), and `ClipboardItem.fileIsInTrash` / `FileGroupEntry.isInTrash` follow the bookmark too (stored path first, so the common case is one `stat`), which makes copy, open, drag and `PasteboardComposer` refuse a file trashed after the copy exactly as they refused one copied from the Trash. **The row gates its buttons on `fileAbsence`** (at the user's request): in the Trash the item stays whole — pin, Vault, delete — but Quick Look, Share and Open are inert, and ↗ becomes "Show in the Trash" (`revealInFinder` now selects the bookmark's resolved URL, so Finder opens the Trash on it and Put Back works); gone from disk, only what concerns the record stays — delete, **unpin and unlock** (never leave an item stuck pinned or locked), re-masking a revealed row, and *Copy extracted text*, since that text is PasteSpace's own and outlives the file (its tooltip then says "kept after the file was deleted", so the one lit button doesn't read as an oversight) — while pin, lock, Quick Look, Share and Open go inert with a tooltip saying why. A row on screen hears about a change at once: `FileWatcher.onChange` → `FileStatusStore.fileChanged`, an `@Observable` per-item `revision` the row keys its status `.task` on (the cache is `@ObservationIgnored`, so only file events invalidate rows, and those are rare).
- **v14 records use.** `useCount` and `lastUsedAt` are written by `DatabaseManager.recordCopies` at the deliberate-use sites — both paste paths, the multi-selection copy, the Quick Look OCR copy, the Data Magic copy — never on selection. They exist early on purpose: usage cannot be backfilled, so anything not counted is gone. Sorting reads them first, but the reason they are worth having is retention — `applyRetention` derives expiry from `timestamp` alone, so an item pasted daily can still be deleted for being old. **Teaching retention and the history limit to read `lastUsedAt` is a separate, deliberate step**, not to be folded into a feature commit. `kind` is `ItemKind.classify`'s answer, indexed so a kind filter is a lookup.
- **Kind is read from plaintext content, never from `contentType` alone.** The first version used `contentType` and the Links and Images filters found nothing: a link is captured as plain text, and an image copied in Finder is a file URL. `ItemKind.classify(contentType:plaintext:sourceApp:)` is the single decision — capture (`handleNewItem`, from the item **before** encryption; the record's content may already be ciphertext), Quick Look saves, and the launch sweep all call it, and `ClipboardItemRecord.init(from:)` deliberately leaves `kind` nil. Text: secrets first (`SensitivityDetector.category(of:sourceApp:)` — the same patterns and validators as auto-vaulting, but silent and independent of the Vault settings), then `ClipboardItem.webURL(inText:)` (shared with `isWebURL`, so a row drawn as a link is exactly a row the Links filter finds), then `CodeLanguageDetector`, then formatted text when the row carries `richContent`, else plain text. Formatting is a **kind**, not a state: kinds combine with OR, so "Plain text" and "Formatted text" side by side mean either — as a state it meant both at once, which is nothing. Files: `ofFile(at:)` by the extension's `UTType` — app/package → other file, trailing slash → folder, then image, audio, video, archive, code (source plus JSON/XML/YAML/HTML/plist), document (PDF, composite content, RTF, plain text, spreadsheet, presentation, e-book) — with fallback extension lists for formats no installed app declares (`.rar`, `.mkv` are dynamic types on a bare Mac). "Other files" means only what no specific kind claims. This puts `CodeLanguageDetector` and the sensitivity patterns on the capture path, a deliberate exception to "detectors run on demand": both are bounded and `Sendable`. `reclassifyKinds()` runs at launch off the main thread, classifying `kind IS NULL` rows every time and every row once when `kindClassificationVersion` is bumped — **bump it whenever `classify` changes**. It decrypts Vault rows to classify them and discards the plaintext immediately, as `sealLegacyVaultFormatting` already does; the result is intentionally coarse ("a password", never the password), which is the one thing a locked row's kind reveals through the filter. Image rows are paged without their blobs.
- History order is user-controlled: every list query sorts by `COALESCE(sortOrder, julianday(timestamp) * 86400.0) DESC`. Inserts get `max(now, MAX(sortOrder) + 1024)` so new captures land on top; reorders write a value between neighbours. Any new list/search query must use the same ordering expression.
- **Copying content again elsewhere in macOS brings it back to the top; copying it out of PasteSpace does not.** `upsertItem` (a re-capture) gives the row a fresh top `sortOrder` unless it is pinned — pins are a curated set — and **even if it was dragged into place**: an exception for dragged rows (`manuallyPlaced`, v15) was tried and removed at the user's request, so that column is unused and kept only because migrations are append-only. A copy *from* the list (click, Return, ⌥Return, multi-selection, recognised text, Data Magic) is recorded in the item's copy history by `DatabaseManager.recordCopies` and never moves it: using an item is not news about it, and moving it rearranged the list under the user's hand. That second half was briefly the other way round and was reversed at the user's request; keep it.
- **A merged copy is analysed under the row that holds it.** When `upsertItem` returns `.deduplicated`, the capture has no row of its own; `handleNewItem` runs document reading and OCR on the existing row instead, only for text it still lacks, and never on a locked one. Before, both ran under the capture's own id — the results went nowhere, and Vision re-ran on every re-copy of the same image.
- Ephemeral Mode (Pro only): on `NSWorkspace.willPowerOffNotification` and on **every** `applicationWillTerminate` set `ephemeralPendingWipe` (+ include-pinned flag); the wipe executes on next launch (flag cleared first), never touching Vault items. The deferral avoids the cold-launch race where StoreKit hasn't confirmed `isPro` yet. A quit the user starts is confirmed first (`applicationShouldTerminate` → `.terminateLater`, `EphemeralQuitConfirmationView`); **a log out, restart or shut down is not**: loginwindow leaves UI-element apps out of the round of apps it waits for ("App is UI Element, do not add it") and sends them the quit only after `setLogoutPointOfNoReturn`, without waiting, so a window there could neither cancel nor delay anything — seen on a real Mac and in a VM, while TextEdit or Xcode could still stop the same log out. `currentQuitReason()` tells the two apart and a power-off returns `.terminateNow`. `willPowerOffNotification` stamps the flag as a power-off begins, and another app can still stop it — PasteSpace is then never asked to quit and the stamp stays — so **Cancel in the confirmation clears it**, `applicationWillTerminate` always rewrites the include-pinned choice, and the launch wipe runs only while `settings.ephemeralMode` is still on (a local preference, so no StoreKit race): a stale flag must not erase history after the user turned the mode off.
- StoreKit 2 (`StoreManager`): single non-consumable `com.pastespace.pro.lifetime` (local config `clipboard_manager/Configuration/PasteSpaceProducts.storekit`); `Transaction.currentEntitlements` at launch, lifelong `Transaction.updates` listener, `finish()` every delivered transaction; offer codes via SwiftUI `.offerCodeRedemption` hosted in a visible key anchor `NSWindow` (macOS 15+). `ProManager` gates features via the `Feature` enum + `canUse…(item:latest…ID:)` helpers (free tier = latest text/image only); all Pro-simulation/reset helpers are `#if DEBUG`. **Offer codes** (the user gives Pro away with them, so they must keep working): Apple accepts codes for a non-consumable from **macOS 15.0** only — in the app, in the App Store and through a redemption link alike — so the paywall shows "Redeem a Code" on 15+ and, below it, says that redeeming needs macOS 15 instead of hiding the option. A redeemed code arrives as an ordinary verified transaction (`Transaction.offer?.type == .code`, logged as "(offer code)"): through `Transaction.updates` while PasteSpace runs, once more there at launch while unfinished, and in `currentEntitlements` from then on. The in-app sheet uses `offerCodeRedemption(isPresented:onCompletion:)`, whose completion is `Result<Void, Error>` (failures are logged), and closing it — for any reason — runs `refreshAfterRedemption()`, which reads the entitlements again so Pro never waits for a relaunch. `StoreManager.onNewPurchase` fires for a grant that happens now (purchase, redemption, App Store delivery), never for one found at launch; Debug builds use it to lift "Reset Pro status", which otherwise hid a real test purchase behind the forced free tier. Test in Xcode with the scheme's `PasteSpaceProducts.storekit` (offer code `PASTESPACE2026` — a one-time-purchase offer code there must carry `paymentMode` (`free`, `payAsYouGo` or `payUpFront`) and `displayPrice`: without them `storekitagent` rejects the **whole** file (`DecodingError.keyNotFound … products[0].offerCodes[0]`), `Product.products` returns nothing and the redeem sheet is inert; edit offers in Xcode's StoreKit editor rather than by hand): the in-app sheet, and Debug › StoreKit › Manage Transactions for a code redeemed outside the app and for a refund.

- **Promoted purchase.** `com.pastespace.pro.lifetime` can be bought from the App Store product page (App Store Connect → the in-app purchase → *App Store Image* → *Promote on the App Store*, "show to all users"); the App Store installs the app if needed and hands the purchase over at launch. `StoreManager.startPromotedPurchaseHandling()`, started first thing in `start()` so a cold launch's handover is not missed, takes it through **one of two routes, never both**: `PurchaseIntent.intents` on macOS 14.4+, and below that StoreKit 1's `paymentQueue(_:shouldAddStorePayment:for:)` via `LegacyPromotedPurchaseObserver`, installed only when `PurchaseIntent` is unavailable. The legacy hook returns `false` — deferring rather than letting StoreKit 1 run the payment — because StoreKit 1 would present its sheet with no key window in a menu-bar app and complete the transaction outside the flow that grants Pro; its `updatedTransactions` is deliberately empty, since every transaction reaches `Transaction.updates`. Both routes end in `purchase(_:)`, the in-app button's anchor-window flow (temporary `.regular` policy + a key-capable window — a bare `product.purchase()` from a handover would have neither), and use the `Product` the handover carries, since `proProduct` may not have loaded yet on a cold launch. `purchase(_:)` ignores a second request while one is on screen or when Pro is already owned. The StoreKit 1 API is deprecated from macOS 15 but builds warning-free because the deployment target is 14.0. Apple documents promoted in-app purchases for iOS only; the App Store Image section *does* appear for this macOS app, which is the evidence the feature applies here — test the handover in sandbox or TestFlight before relying on it.

## 8. Logging
- `os.Logger` via the `Logger` extension in `Utilities/Logger.swift` — exactly seven categories: `engine`, `persistence`, `ui`, `hotkey`, `vault`, `ocr`, `app` (subsystem = bundle ID). Clipboard content and paths use `privacy: .private`; bundle IDs/types may be `.public`. No `print`.
- The category *strings* differ from the property names — `ClipboardEngine`, `Persistence`, `UI`, `Hotkey`, `Vault`, `OCR`, `App` — and predicates must use the strings. Stream everything, or narrow to one category:

```bash
log stream --predicate 'subsystem == "com.pastespace.clipboard-manager"' --level debug
```

```bash
log stream --predicate 'subsystem == "com.pastespace.clipboard-manager" AND category == "UI"' --level debug
```

## 9. Response Format
- Language: reply in the language the user writes in; code, identifiers, comments and log strings in English.
- Code first, then ≤5 bullets (root cause / trade-offs), tag decisions `[reversible]` or `[locks-in architecture]`.
- For build errors/logs: exact file:line, one-sentence root cause, minimal patch.
